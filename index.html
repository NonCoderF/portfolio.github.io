04 / Adaptive Exercise Recognition

From Rule-Based Detection
to Personalized ML.

A Vantage Fit case study in production computer vision, anti-cheat design, TensorFlow Lite inference, and iterative engineering.

Problem / Iteration / Production ownership

Detect real exercise movement with a mobile camera, then keep improving after real users found ways to break it.

The requirement was to detect exercises such as squats using the mobile camera. I used an existing pose/skeleton detection API to obtain labeled body landmarks; I did not build the pose detector itself. The engineering work was the recognition system layered on top: movement tracking, validation gates, anti-cheat checks, ML classification, rep counting, and personalization.

Build -> Observe -> Users Break It -> Understand Why -> Improve -> Repeat
Ownership signals
  • Designed recognition logic around existing pose APIs.
  • Investigated production failures and adversarial behavior.
  • Combined computer vision with Android device context.
  • Migrated deterministic rules to learned classification when complexity justified it.
  • Designed a user-specific feedback loop without implying on-device self-training.
Camera Frame->Pose Landmarks->Joint Movement Tracking->Waveform / Cycle Detection->Confidence Threshold->Squat Count
WHEN USERS STARTED CHEATING

Recorded sessions became engineering feedback.

REAL-WORLD TESTING

During real-world testing, I used background session recording to understand how users were actually interacting with the feature. Normal QA could validate expected paths, but it could not predict every creative way someone would try to game the detector.

Some of the funniest user behavior produced some of the most valuable engineering lessons. Users often believed they were defeating the camera algorithm itself. In reality, each attempt simply exposed another assumption in the system that could be measured, understood, and hardened.

Unexpected user behaviorFalse assumptions in the algorithmNew cheating strategiesEnvironmental reliability issues
Iteration 01

Rule-Based Squat Detection

The first implementation tracked relevant joints over time and modeled the squat as a movement cycle similar to a sine waveform. If the observed cycle matched the expected squat pattern at roughly the original 90%+ confidence threshold, the system counted one squat.

Exploit Found

Lying Down

From recorded session data, I saw users lying down and repeatedly moving their legs. Because the first detector focused heavily on movement cycles, that behavior could sometimes resemble a valid squat pattern. I added standing-posture validation and skeletal landmark orientation checks, so a valid cycle only counted when the body posture was also valid.

Valid Squat Cycle+Standing Posture=Valid Squat
Fix

Phone Orientation

The next loophole was phone orientation. Users discovered that changing how the phone was positioned could interfere with assumptions made by the camera coordinate system. I solved it with Android device-orientation APIs, requiring the session to start only when the phone was in an expected valid orientation.

Instead of making the vision algorithm unnecessarily complicated, use device information the operating system already provides.
Input Gate

Poor Lighting and Landmark Jitter

Poor lighting made pose landmarks unstable, creating motion noise and occasional false detections. I introduced a lighting quality gate so bad input was rejected before reaching the expensive recognition pipeline.

Garbage input should be rejected before reaching the expensive recognition pipeline.
UPDATED VALIDATION PIPELINE

Reject weak signals early.

Camera->Lighting Validation->Device Orientation Validation->Pose Detection->Standing Validation->Exercise Detection
ML Upgrade

Moving Beyond Hand-Written Rules

As the feature matured, the waveform approach became harder to generalize. I replaced the sine-wave classifier with a TensorFlow Lite model trained to recognize multiple exercise patterns, initially including squats, push-ups, and jumping jacks.

The pose system still provided body movement data, but classification moved from fixed rules to learned movement recognition.

CameraPose LandmarksFeature / Motion RepresentationTensorFlow Lite Exercise ClassifierExercise + ConfidenceValidation GatesRep Counter
Personalized Learning Loop

The system did not only learn what a squat looks like. Over time, it learned what your squat looks like.

Instead of treating every user as if the system was seeing them for the first time, completed exercise sessions generated valid movement data for a separate training/adaptation pipeline. The app used TensorFlow Lite for inference; training and adaptation happened separately, and updated personalized models were used for future inference.

Range of motionSpeedBody proportionsJoint trajectoriesExercise style
Generic Model->User Performs Exercise->Valid Movement Data->User-Specific Training / Adaptation->Personalized Model->Improved Recognition
Final Exploit

Playing a Squat Video

Eventually, users tried playing prerecorded squat videos in front of the camera. The camera could still see a person, correct body landmarks, and valid squat motion. Since standard Android devices do not provide reliable universal depth sensing that simply solves this, I avoided expensive screen detection or monocular depth estimation and introduced a device-sensor / physical-context handshake using Android APIs.

When one sensor can be fooled, validate it with an independent signal.
Defense in Depth

Camera + Device State

The vision result was no longer trusted by itself. The system required agreement between the camera / pose signal and an independent device physical-state / sensor signal before recognition was accepted. This acted as a lightweight liveness check without exposing sensitive anti-cheat implementation details.

Computer vision surrounded by context.

Engineering Lessons

What This Project Taught Me

Production engineering is iterative. A feature can become a learning system instead of remaining static.

Start with the simplest solution that solves the problem.Let real-world data expose incorrect assumptions.Users interact with systems in ways developers never predict.Anti-cheat systems work better when independent signals are combined.Do not introduce ML simply because ML sounds impressive.Move from deterministic rules to learned models when complexity justifies it.Reject unreliable input early.Technical ownership means understanding why an architecture evolved.
Open Full Technical Breakdown

Problem

Detect camera-based exercise movement without claiming ownership of pose estimation itself. The algorithm consumed labeled skeletal landmarks and reasoned about exercise motion, validity, and rep count.

Initial Approach

Joint trajectories were tracked over time and compared against the expected squat cycle. The waveform confidence threshold gave the first working version a simple, inspectable decision rule.

Real-World Failures

Background session recordings revealed lying down, phone rotation, poor lighting, jittery landmarks, and prerecorded video attempts. Each one exposed a wrong assumption about the input stream that normal development testing had not produced.

Iterations

Each failure added the smallest useful validation layer: standing posture, skeletal landmark orientation checks, phone orientation, lighting quality, Android sensor/physical-context validation, and eventually learned movement classification.

Final Architecture

Recognition became a validation-gated system: camera input, environmental gates, existing pose landmarks, posture validation, TFLite inference, sensor-based liveness checks, rep counting, and a separate personalization/training pipeline.

06 / ENGINEERING CHALLENGES

Constraints are design material.

01

Room acoustics

Reflections and standing waves can make an affordable system feel uneven.

Analysis → Solution → Result

Map surfaces and listening position; use symmetry, toe-in and calibration for a wider, more even field.

02

Cable routing

A living room cannot feel like a wiring closet.

Analysis → Solution → Result

Separate signal and power runs, plan before installation, and keep serviceable paths hidden.

03

Power budget

More channels do not automatically mean more usable headroom.

Analysis → Solution → Result

Match amplifier behavior, speaker efficiency and realistic listening levels with measured headroom.

04

Compatibility

Affordable hardware often speaks different signal languages.

Analysis → Solution → Result

Trace every connector and conversion point, then validate each hand-off for minimal latency.
